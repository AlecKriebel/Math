This helper is prepared software. No real deposit, upload, publication, tracker append, PR edit, git mutation, merge, or science edit was performed. The parent supplies the three final reviewed assets and all legacy metadata, fully reads the actual spec, and controls every production command.

State, evidence, and native snapshot paths must stay inside this helper’s own private custody directory.

Phases are explicit:

1. `inspect --spec SPEC` hashes and checks the exact local assets/spec and performs only target-sheet identity/header GETs. The parent reviews it and approves its exact raw spec SHA256 for staging.
2. `stage --spec SPEC --approved-spec-sha256 SHA` creates one production draft, uploads exactly three frozen assets, PUTs exact legacy metadata, verifies every actual legacy field/file, and captures authenticated native draft/access/file readbacks. It returns a private `NATIVE_METADATA_ACCESS_SNAPSHOT.json` path and SHA. These are exact canonical JSON bytes serialized from the actual parsed native metadata/access/custom-fields object; the pinned Zenodo client returns parsed JSON rather than a raw authenticated HTTP envelope. Full parsed native readbacks remain private; no HTTP status field is invented for them. Status is `staged_pending_native_acceptance`; the snapshot has not received technical acceptance yet.
3. The parent fully reads that actual native snapshot and complete private readbacks, checking native author/ORCID/title/description/type/license/date/access/files against all supplied metadata. This is the parent's technical acceptance gate under the user's already authorized publication request, not an additional user permission request. `publish --approved-spec-sha256 SHA --confirm-id ID --approved-native-sha256 NATIVE_SHA` requires exact snapshot bytes, rechecks all staged metadata/files, and sends one publish POST. Authenticated submitted/native and public legacy/native metadata must match; all three public downloads are independently hashed for exact SHA256/MD5/size.
4. `tracker --approved-spec-sha256 SHA --confirm-id ID --approved-native-sha256 NATIVE_SHA` freshly re-verifies publication and all public asset bytes. It checks native spreadsheet/gid/title/headers, reads only the DOI column for deduplication, accepts normalized bare or doi.org forms, and permits at most one match. An already exact row produces no append; a conflicting or duplicate DOI row stops. After another fresh identity/header/absence read it sends ONE append with `RAW`, `INSERT_ROWS`, exactly one four-cell row. It verifies exact native returned spreadsheet/counts/row range, then batchGets that returned row plus header and checks all values, followed by a unique DOI scan.
5. `reconcile --approved-spec-sha256 SHA [--approved-native-sha256 NATIVE_SHA] [--recover-id ID]` performs GETs only. Published outcomes require the separately accepted native snapshot. An unknown creation ID requires a root-supplied recovery ID; no account search or restage is attempted. An unknown append has no fabricated returned-range receipt: reconciliation can report one exact observed DOI row while explicitly recording that the append response is unavailable. Stale absence reads cannot prove an unknown write failed.
