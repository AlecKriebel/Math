## Scope and independence

Mathematical Biology package bytes; both release builders; the v1.1.2
hardening verifier; public-release instructions; source ZIPs; checksum
manifests; ignored release assets; and the moved superseded replay evidence.
I did not run `verify_full.sh` or `verify_regenerate_all.sh`, and I make no new
assessment of the unchanged mathematical theorem.

The repository was at source commit
`888d90599d8487de3f3c2b425edddfd34bc82505` with the v1.1.2 revision still
uncommitted.  The advertised v1.1.2 tag and GitHub Release did not exist when

## Submission-blocking findings

### R1. The active public-release claim is false, and the local release assets are stale

There is currently no public tag or GitHub Release named
`stc-jc-sharp-boundary-v1.1.2`.  Nevertheless `STATUS.md`,
`REVIEW_DISPOSITION.md`, `release/PUBLIC_RELEASE_ASSETS.md`, the manuscript
data/code URL, and submission metadata use present-tense language saying that
the v1.1.2 assets are published.

More seriously, the ignored files currently present under `release_artifacts/`
are the old v1.1.1 release, not a merely unpublished v1.1.2 candidate:

- `RELEASE_ENVELOPE.json` binds commit
  `a1f4297bdf87fa673fbeec1633743654e766b91b`;
- the archive marker contains that same commit;
- the engineering report names annotated tag
  `stc-jc-sharp-boundary-v1.1.1`;
- the archive's `RELEASE_METADATA.json` states release revision v1.1.1; and
- its PDF hashes are the earlier
  `2577a6b2...` and `51b89b92...`, not the current package hashes above.

The tracked active `RELEASE_METADATA.json` is also pre-seal: it still records
the old PDF/source-ZIP hashes and lacks the newly required journal and v1.1.2
review artifacts.  A direct bounded run of
`reproducibility/verify_active_release.py` therefore fails with
“release artifact inventory is incomplete or contains stale entries.”

This is a hard hold.  The v1.1.2 source must first be frozen, core-sealed,
replayed from a clean checkout, archived, envelope-sealed, tagged, pushed,
and published with newly generated assets.  The public URLs and present-tense
claims may be retained only after a download-and-hash replay confirms that
the public assets are those new bytes.

### R2. The source-ZIP build instructions name directories that do not exist after extraction

All three root `BUILD.md` files say to build from `source/paper/` and
`source/supplement/`.  Their ZIP layouts do not contain a `source/` directory:

- the bioRxiv ZIP contains `paper/` and `supplement/` at archive root;
- the journal ZIPs contain
  `SB_LaTeX_Source/paper/` or `JMB_LaTeX_Source/paper/`.

The sources themselves are complete and compile from the actual paths, but a
reader following the supplied instructions receives an immediate missing-
directory error.  Either preserve the `source/` prefix in every ZIP or
generate ZIP-specific build instructions.  Add an extracted-ZIP smoke test
that follows the documented commands literally and compares the rebuilt PDF
to the packaged PDF.

### R3. The checksum verifier accepts incomplete manifests

`verify_sum_file()` validates only rows that happen to remain in a manifest;
it does not require an exact bijection between expected portal files and
manifest rows.  I copied each package to a temporary directory, reduced its
manifest to one valid line, and observed:

```text
biorxiv_submission ACCEPTED_TRUNCATED_MANIFEST
systematic_biology ACCEPTED_TRUNCATED_MANIFEST
```

Thus deletion of the checksum commitment for a main PDF, source ZIP, cover
letter, or metadata file can pass the new hardening verifier.  Require the
exact expected filename set, reject duplicate rows and path traversal, and
add mutations for a deleted row, duplicate row, renamed target, and valid
hash assigned to the wrong filename.

### R4. The targeted hardening verifier does not validate release provenance

`verify_release_hardening.py` prints a `VERIFIED` result containing the
purported public release URL even while the release is absent and local
release assets are v1.1.1.  It checks URL strings, not release existence,
envelope revision, source commit, or asset hashes.  The broader active-release
verifier catches part of this, but the new review gate's own success message
is misleading.

Keep network publication checks out of an offline mathematical replay if
desired, but split the statuses explicitly: “package candidate verified”
before publication and “public release verified” only after a bounded
post-upload check downloads the tag, envelope, manifest, and all assets and
compares their hashes.  The final release transcript must record that check.

### R5. The public release manifest is neither flat-download replayable nor complete as described

`release/PUBLIC_RELEASE_ASSETS.md` says that
`RELEASE_ASSET_SHA256SUMS` contains an independent line for every one of the
eight release assets.  The current manifest has six rows: it omits the
envelope and necessarily omits itself.  Its rows also use monorepository paths
such as
`s_tc_jc_landmark_closure/release_artifacts/clean_clone_transcripts/...`,
whereas GitHub downloads the assets into one flat directory under their
basenames.  Consequently a reader cannot download the eight assets together
and run the manifest directly.

Create a public flat manifest using release-asset basenames, include the
envelope hash, and state clearly that the manifest itself is the downloaded
trust anchor (or supply a separately published sidecar/signature for it).
Retain a separate repository-relative internal manifest if the local verifier
needs one.  Add an exact download-and-`shasum -c` command to the public replay
instructions.

### R6. The JMB supplementary-information file does not satisfy the journal's stated identification requirements

The current official JMB instructions say that each supplementary file must
include the article title, journal name, author names, affiliation, and
corresponding-author email, and that the article should cite it as an “Online
Resource.”  The generic six-page supplement contains the article title,
author name, and affiliation, but not “Journal of Mathematical Biology” or
the email address.  The JMB article refers generically to “the supplement,”
not “Online Resource 1.”

Generate a JMB-specific supplement/title block with the missing journal and
contact information, include the corresponding source in the JMB ZIP, and
make the JMB manuscript/upload metadata identify it consistently as Online
Resource 1.  This does not require altering the canonical bioRxiv supplement.

## Nonblocking quality corrections

1. Both cover letters put a full stop inside the quoted manuscript title and
   then continue the sentence (`Networks.''`).  Remove the title-internal
   punctuation so the rendered quotation is typographically clean.
2. The Systematic Biology Tectonic build emits an `lineno.sty` invalid-UTF-8
   replacement warning.  The PDF builds deterministically, and I found no
   resulting content loss in extracted text, so this is not currently a
   blocker.  Record or eliminate the warning rather than silently allowing
   it if a different TeX engine is used for the final clean replay.
3. The moved historical directory would benefit from its own SHA-256 manifest
   covering the preserved records.  Its present labelling is already clear,
   so this is archival hardening rather than a release blocker.
4. The official OUP and bioRxiv pages were protected by anti-bot responses in
   this clean-room check.  Their upload maps already instruct the human author
   to recheck current portal fields.  Perform that human browser check on the
   submission day; do not treat the dated preparation notes as immutable
   portal facts.

After R1--R6 are corrected, the release candidate should pass all of the
following before this review can change to PASS:

1. package-local exact-manifest checks with the new deletion/misassignment
   mutations;
2. literal extracted-ZIP build commands and byte comparison;
3. `verify_active_release.py` against newly sealed v1.1.2 metadata;
4. clean quick/full/regenerate-all transcripts bound to the final immutable
   commit;
5. extracted-archive replay;
6. public tag/release lookup followed by download and flat-manifest
   verification; and
7. a JMB package check for journal/contact identification and Online Resource

The current manuscript mathematics was not refuted by this package audit,
and the deterministic builders themselves performed well.  The exact bytes
are nevertheless not yet a truthful, self-verifying submission release.

## 5. Flat seven-row public manifest — design PASS, two gate defects remain

The repaired architecture is the correct non-self-referential one:

- the GitHub Release must contain exactly eight flat-named assets;
- `RELEASE_ASSET_SHA256SUMS` must contain exactly seven rows, covering every
  other asset, including `RELEASE_ENVELOPE.json`;
- the manifest itself is the downloaded trust anchor; and
- the envelope separately binds the source commit, archive, transcript
  digests, core metadata, and final outcome.

Synthetic parsing tests confirmed the exact 7-of-8 relation and rejected a
deleted row, duplicate row, nested-path row, and wrong digest/name pairing.
The downloaded asset-set check is also exact rather than subset-based.

Two mandatory corrections nevertheless remain:

1. **The documented manifest-hash record is not implemented.**
   `release/PUBLIC_RELEASE_ASSETS.md` says that the manifest's own hash is
   recorded by the release-time public verifier and final release transcript.
   The JSON emitted by `verify_public_release.py` does not include that hash,
   so a transcript of the command cannot record it.  Either add a field such
   as `release_asset_manifest_sha256` to the verifier's final JSON (preferred)
   or remove the unsupported sentence.  The verifier should have a bounded
   regression asserting the field equals the digest of the downloaded
   manifest.

2. **A lightweight tag currently passes the purported annotated-tag gate.**
   `resolve_public_tag()` immediately accepts a ref whose object type is
   `commit`; only the other branch checks and peels an annotated tag object.
   This contradicts `release/UPLOAD_RELEASE_ASSETS.md` and the review
   disposition, both of which specify an annotated tag.  Require the ref
   object type to be `tag` and then require its peeled object type to be
   `commit`, or consistently weaken every document to allow a lightweight
   tag.  Given the intended immutable release protocol, enforcing the
   annotated tag is the cleaner correction.  Add a mutation/unit seam proving
   that a lightweight-tag response is rejected.

These are not requests to perform the public upload now.  They concern the
local code that will decide whether that upload is authoritative.
