## Mandatory finding R2-F1 — ready transition uses guards from before the native readbacks

**Severity: medium; reproduced twice.** `verify_and_merge.py:24–32` validates current release context, publication/tracker and prepared-receipt fingerprints. Lines 56–60 validate the current PR and its actual commit. Native tree/body/Queue/scope reads then run through line 125. Lines 133–137 use the cached `pr` object to create `NATIVE_READY_ATTEMPT.json` and POST `markPullRequestReadyForReview`. The next current release validation is line 148, after the irreversible draft-to-ready transition. Fresh current PR identity is checked only after that transition, at lines 139–141.

Concrete isolated counterexample A: start from a fully consistent mocked integrated PR, receipts, artifact pair and clearance. The mocked `compare` GET at line 123 changes only the synthetic local clearance's `release_cleared` to false. The helper still creates the ready intent and sends **one ready POST**. Line 148 subsequently raises `Final release not cleared`, so **zero merge PUTs** occur. This is an actual stale-guard transition, although the merge gate works.

Counterexample B: the same last read changes only the mocked current PR head from the reviewed `bbbb…bbbb` commit to an unreviewed `dddd…dddd` commit. The cached PR node ID is still used for **one ready POST** on the current PR. The subsequent PR identity check raises `Wrong expected native head/branch`, and again no merge occurs. This does not depend on fabricated provider responses or corrupt receipt schemas: it models a head change after the earlier read, precisely the class of stale-state transition that the existing later checks address.

**Required repair:** immediately before creating a new ready intent and issuing its POST, revalidate the current context against the initial context, publication/tracker evidence against the exact initially accepted receipts, and the prepared receipt's identity/fingerprint against the accepted record. Fetch the current PR again and require the exact expected head, branch, repositories, base, open/unmerged state and appropriate draft state. If it is already ready, do not repeat the POST; handle the observed state through the existing read-only/reentry discipline. Keep the post-transition and pre-merge checks. This narrows the stale-state interval; GitHub's ready mutation has no expected-head compare-and-swap parameter, so a fresh preflight cannot promise impossible remote atomicity.

The shared lock does not repair this gap: it serializes these helpers, while release-authoring changes and remote PR head changes are outside that lock. Neither reproducer changes the reviewed helper bytes or the native scientific artifacts. See the two `defect_reproduced` records in `MOCKED_WORKFLOW_RESULTS.json` and `ready_clearance_change`/`ready_head_change` in the probe source.

## Additional finding R2-O1 — newly created intent directory entries are not synced

**Severity: medium; persistence deduction with explicit evidence limit.** `release_binding.py:144–147` opens each intent with exclusive creation, writes it, flushes it and calls `os.fsync` on the regular file descriptor. It does not sync the containing directory before returning to the associated provider mutation. All six intent types use this primitive.

The isolated descriptor trace records exactly **one regular-file fsync and zero directory fsyncs**. Therefore ordinary process interruption and competing invocations have a checkable barrier, but durability of the newly created directory entry across a system/power crash is not established. Under the usual file-versus-directory durability model, the file contents may have been flushed while the new name is not durably linked. A subsequent restart can then lack the very marker that promises no repeated uncertain mutation. This is a gap in the stated durable-intent guarantee; it is not evidence that an actual crash or duplicate mutation occurred.

**Required repair:** after the intent file has been fully flushed, sync its parent directory before allowing any associated provider action. Fail closed if that sync cannot be confirmed on the supported platform; preserve the intent and perform no mutation. Ensure any newly created ancestor needed to reach an intent also has the required durable name linkage. Test successful file-then-directory sync ordering and an injected directory-sync failure that leaves the provider mock uncalled. A more elaborate crash simulator or hardware study is outside this review's scope and is unnecessary for this source correction.
