# Paper-by-paper website review protocol

This records the workflow requested by Alec on 24 October 2026. The pilot is
one paper. A persistent all-papers goal has not been created; the user intends
to set it after reviewing the pilot.

1. Select an existing published paper and identify its exact edition, DOI,
   status, and relationship to other versions. Preserve original dates.
2. Download the public PDF and supporting package. Check advertised hashes
   and sizes; record SHA-256 identities. Safely extract the source. Review the
   actual published edition rather than silently substituting newer local work.
3. Define the exact claim, hypotheses, success criteria, and boundary cases.
   Read the entire manuscript. Assign materially distinct analytic,
   computational where applicable, and source/scope reviews. Reviewers should
   initially avoid previous positive assessments. Use an adversarial check
   before promotion. Preserve checkable derivations, code, receipts, and gaps.
4. Require no unresolved substantive defect in the promoted claim. A positive
   review means no such error was found within its stated scope; it does not
   guarantee correctness, historical firstness, or human peer review. Repair
   or explicitly resolve a defect before promotion. Do not quietly alter an
   archived paper.
5. Add one stable page per distinct work to the existing Firebase website at
   Desktop/alec-dev/aleckriebel.com, under public/research/. Match the user's
   blog article templates: white background, Arial, ordinary links, simple
   headings, a single column, and a plain list for the index. The user rejected
   decorative cards, badges, large editorial typography, and a sidebar.
6. Include the real title, author/ORCID, publication/version dates, accurate
   status, full visible abstract, a brief accessible explanation, exact result
   and limits, verification summary, AI disclosure, DOI, unchanged downloads,
   citation, and credited background. A professional public invitation may
   identify useful substantive collaborations; do not promise authorship for
   endorsement. User explicitly authorized this page invitation. Do not
   contact an individual on the user's behalf.
7. Provide citation metadata, a same-directory direct searchable PDF, canonical
   URL, structured scholarly data, and a sitemap entry. Preserve the Zenodo
   DOI and dates. Do not invent a journal, acceptance, firstness, or exact value
   where only an upper bound is proved. Do not publish internal impact scores
   as quality badges.
8. Independently check copy, local links/anchors, dates/schema, file identities,
   and the limited diff. Inspect desktop and phone layouts. Publish only the
   intended website changes through its existing hosting workflow; verify
   the live content and download identities. Keep an evidence-backed log.
9. For this first case, the user reviews and approves before any GitHub Pages
   redirect. No predecessor page for this particular paper was found in the
   current Math/docs catalogue, so no redirect was prepared. Future redirects
   must map an actual old paper URL to its corresponding new page and respect
   the capabilities of static GitHub Pages. Do not redirect all old pages to
   the research homepage.

The index lists only papers whose individual pages have completed this
workflow. It links to the older archive while the collection is expanded.
