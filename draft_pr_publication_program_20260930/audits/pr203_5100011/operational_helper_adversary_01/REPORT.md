## Findings, repairs and regression evidence

### Resolved: unknown stage outcome could be retried without a guard

Original `publication_operations_01/publish_exact.py`, SHA25628017272fc517b38fd68535272e9f99671dbcc17e69ff633c4e7b05fcaabd2cc, guarded stage/publish only by the successful mode JSON. That file is written after the child returns and its output is parsed. A create request could reach Zenodo but lose its response, or create an ID whose kit state could not be saved due to disk failure. The wrapper then left no stage.json. Existing stdout/stderr text files did not block a second stage invocation. The kit warns about this condition but does not persist a guard when no ID is known; another invocation could create a duplicate draft.

Root added exclusive STAGE_INFLIGHT/PUBLISH_INFLIGHT records before subprocess launch. The writer flushes/fsyncs the marker file and fsyncs its directory. Marker existence blocks every subsequent mutation attempt even when successful result JSON is absent. Read-only inspection remains available. Successful result JSON is also exclusive and durable. I checked the actual new code: the durable marker call occurs at line38 and the child launch at39, and the marker guard covers both stage and publish. Disk/parse/output failures after launch now leave a fail-closed attempt marker. Partial marker writes also leave an existing file and never launch the child. Recovery may require read-only account/state reconciliation; automatic restaging is deliberately unavailable.

The pinned repository kit itself matches the expected API: stage uses a manifest/environment-specific saved state, resumes an identified draft rather than creating another, verifies exact metadata and file set/checksums, and publish verifies the saved exact confirmation ID. Its publish path performs one POST and then GET reconciliation, including an already-published path. Wrapper finalization additionally requires DOI resolution200/resolved and independently downloads/hashes every intended public file. No unknown outcome is counted as publication success.

### Resolved: tracker recovery forgot the original foreign-row baseline

After a successful append with lost response/readback, a later recovery compared only its new before1/before2 reads against after. Foreign rows removed between the original append and recovery could therefore be absent from all three fresh reads while foreign_rows_retained was set true.

Root now pins the original full pre-append CLI receipt by filename, SHA256/bytes and row count inside a durable APPEND_INFLIGHT record. `original_baseline` authenticates its path/pin, successful CLI/API result, header and row count, and binds its DOI/row to the intended append. Receipt persistence now flushes/fsyncs each file and its directory.

When the original foreign row is absent from recovery before1/before2/after, the original predicate accepts but the repaired original-baseline predicate rejects. A retained original baseline plus one new dummy row is accepted. No dummy DOI, scientific postimage, tracker receipt or publication fact was written to an external service or scientific artifact.

The remaining duplicate controls are sound in the reviewed normal workflow: an existing final receipt refuses another append; an inflight operation with absent DOI refuses retry; exactly one matching DOI with byte-exact expected row can be recovered read-only; unexpected or duplicate matches fail.
